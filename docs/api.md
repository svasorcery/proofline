# Replay API и операторский процесс

API работает с синтетическими обращениями в PostgreSQL. Оно сохраняет разборы и решения, но не выполняет предложенные действия, не отправляет сообщения и не разрешает выплаты. Полный набор маршрутов и DTO доступен в `/docs` и `/openapi.json` запущенного приложения; бизнес-контракт находится в [spec.md](spec.md).

## Запуск

Из корня репозитория:

```sh
docker compose -f infrastructure/compose.yml up -d --wait db
docker compose -f infrastructure/compose.yml run --build --rm app migrate
docker compose -f infrastructure/compose.yml run --rm app seed
docker compose -f infrastructure/compose.yml up -d --wait app
python examples/replay_walkthrough.py
```

Адрес — `http://127.0.0.1:8000`. Образ приложения работает от непривилегированного пользователя. PostgreSQL доступен только внутри Compose-сети; на хост опубликован только API на loopback. Миграция и seed — отдельные команды, запуск сервера их не выполняет. Повторный seed добавляет только отсутствующие V01–V06 и не перезаписывает пользовательские изменения.

Walkthrough выполняет явные HTTP-команды в V04: replay → блокировка → исправленная дочерняя версия → подтверждение разбора. Это сценарий демонстрации роли оператора, не автоматическое одобрение результата моделью. Требование получить подтверждения остаётся в `follow_up` и не исполняется. Если входы V04 были изменены, replay корректно откажет; скрипт не сбрасывает данные ради прохождения.

`docker compose -f infrastructure/compose.yml stop` останавливает локальное демо, сохраняя том. Удаление тома — отдельное разрушительное действие и не часть обычного запуска.

## Порядок HTTP-команд

Все предметные маршруты имеют префикс `/api/v1`.

1. `GET /cases` и `GET /cases/{id}` возвращают версию обращения, источники и независимый признак выполняющегося анализа. Фильтр `status`, `limit` 1–100 и `offset` применяются на сервере.
2. `GET /cases/{id}/replay-options` возвращает только совместимые записи. `POST /cases/{id}/runs` принимает `mode`, `replay_id`, `expected_case_version` и обязательный заголовок `Idempotency-Key`.
3. Ответ run содержит `proposal_revision_id`; `GET /proposals/{revision_id}` возвращает body, исходный snapshot, привязки версий, проверки, отдельные фрагменты и решение.
4. `POST /proposals/{revision_id}/revisions` принимает полный исправленный `body`, `reason` и `expected_case_version`. Создаётся и активируется дочерняя версия; исходный ответ сохраняется.
5. `POST /proposals/{revision_id}/decision` принимает `kind=approve|reject`, `reason`, `expected_case_version` и `Idempotency-Key`. Actor всегда задаётся сервером как `demo_operator`.

Остальные команды позволяют создать обращение, зарегистрировать источник без текста или с текстом, добавить новую текстовую версию, изменить метаданные/порядок/включение источника, выбрать его существующую версию, активировать кандидат и повторно проверить разбор. Изменения источников возвращают обновлённую карточку обращения; точный текст версии читается отдельным GET-маршрутом источника.

Примеры запросов и актуальная схема ответов доступны через OpenAPI. [replay_walkthrough.py](../examples/replay_walkthrough.py) — выполняемый пример без стороннего HTTP-клиента.

## Версии и конфликты

`Case.version` начинается с 1 и защищает команды от потерянных обновлений. Каждый изменяющий запрос передаёт прочитанную версию. Конфликт возвращает `409 CASE_VERSION_CONFLICT`; клиент перечитывает карточку и принимает решение о повторе. Сервер не перезаписывает данные по устаревшей версии.

`content_revision` меняется при изменении входа анализа. Переименование самого обращения меняет только `version`. PATCH, который не изменил значения, не повышает счётчики и не делает одобрение историческим. Создание новой версии текста — отдельное событие даже при одинаковом тексте: привязка к версии изменилась.

Текст SourceVersion нормализуется по переносам строк один раз и дальше неизменяем. Смена входа делает прежний разбор `stale`; старые цитаты продолжают ссылаться на прежнюю версию и SHA256. Старое решение сохраняется, но `decision_current=false`.

Генерация выполняется между двумя короткими транзакциями. Сначала сохраняется `running` run со снимком; затем выполняется replay без удержания блокировки Case. Завершение использует compare-and-set по статусу и владельцу. Результат активируется только если `Case.version` не изменилась; иначе остаётся кандидатом. После перезапуска незавершённые run предыдущего процесса получают `PROCESS_INTERRUPTED`; запоздалый обработчик их не переписывает.

Процесс API должен быть один. Несколько workers/replicas не поддерживаются; команда `proofline serve` запускает одного worker. Восстановление владельца рассчитано на перезапуск этого единственного процесса. Если БД недоступна при старте, восстановление выполняется перед первой успешной readiness-проверкой или предметным запросом после её возвращения; до этого API не объявляет себя готовым.

## Replay, проверки и решения

Replay сравнивает канонический digest обращения, запрошенных фактов, справочного контекста, упорядоченного каталога и выбранных текстов. UUID версий БД в digest не входят, но сохраняются в source bindings. Изменённый вход даёт `REPLAY_INPUT_MISMATCH`; возврат к одному из записанных условий снова даёт соответствующую запись.

Этот digest описывает snapshot приложения и не является хешем исторического prompt. Метаданные каталога детерминированно восстановлены из синтетических fixtures; точный prompt, policy/schema hashes, raw response и recorded usage сохраняют отдельное происхождение. `generation_profile.new_model_call=false`, `usage_origin=recorded`: записанные токены не выдаются за расходы нового вызова. Содержимое кейсов, каталога, prompt/output, metadata и профиля проверяется по хешам при загрузке.

Ключ идемпотентности уникален в пределах операции и обращения. Для run первый завершённый запрос возвращает 201; точный повтор — 200, а повтор во время выполнения — 202. Другое тело с тем же ключом даёт `IDEMPOTENCY_CONFLICT`. Для решения первый результат — 201, точный повтор — 200 с тем же записанным решением. Проверка ключа выполняется до проверки текущей версии, чтобы повтор уже выполненной операции не исполнялся заново.

Состояния `active`, `stale`, `validation_current`, `decision_current` возвращаются отдельно. Успешная runtime-проверка всегда оставляет `needs_operator_review`. Подтверждение повторно проверяет тело и снимок под блокировкой Case; блокирующие ошибки дают `VALIDATION_BLOCKED`. Отклонить заблокированный текущий разбор можно с причиной. Финальное решение по одной версии только одно; для пересмотра создаётся дочерняя версия.

Изменение validation profile делает прежнее решение историческим. Явная повторная проверка создаёт новый ValidationCheck, но сама по себе не обновляет решение. История проверок доступна в `validations`, последняя — в `latest_validation`. Семантические изменения валидатора требуют новой версии профиля, а не перезаписи старых проверок.

## Ошибки и локальная конфигурация

Ошибки имеют поля `code`, `message`, `details`, `request_id`; request ID также находится в заголовке `X-Request-ID`. В ответ не попадают raw validation input, строки исключений или параметры соединения. Невалидные типы/поля/UTF-8 JSON дают 422; превышение лимитов — 413; конфликты — 409; недоступная БД или ненастроенный live — 503. NUL, NaN и Infinity отклоняются до PostgreSQL; текст не обрезается и не исправляется.

Начальные лимиты: 8000 символов обращения, 20 источников, 20000 code points на источник, 80000 выбранных символов. Их можно изменить через Settings/env. `/health` показывает работоспособность процесса, `/ready` проверяет реальную версию миграций. Отсутствие live-ключа не мешает replay readiness. `/capabilities` сообщает доступность режимов, словари, профиль проверок и лимиты без секретов.

`DATABASE_URL` требуется для запуска на хосте. В Compose он задаётся для приватного сервиса `db`. `APP_ORIGIN` задаёт разрешённый origin; дополнительные dev-origins — JSON-массив `DEV_ORIGINS`. Unsafe-запросы с чужим Origin отклоняются; запросы CLI без Origin разрешены. При другом порте API задайте и `PROOFLINE_PORT`, и соответствующий `APP_ORIGIN`. Безопасные локальные примеры — в [.env.example](../.env.example).

Live-адаптер ещё не реализован. Запрос `mode=live` возвращает `LIVE_NOT_CONFIGURED`, не создаёт run и не переключается на replay. Это локальное синтетическое демо, а не промышленная авторизация или внешняя эксплуатация.

## Настроить после согласования live-приёмки

На backend задаются `LIVE_ENABLED=true`, `LLM_PROVIDER`, отдельный `LLM_API_KEY`
и явно выбранный `LLM_MODEL`. Модель и ключ не имеют рабочих значений по умолчанию.
Пользователь меняет окружение и пересоздаёт только app выбранного Compose-проекта;
правки кода, сборка собственного форка и миграция БД не нужны.

| `LLM_PROVIDER` | Протокол и фиксированный endpoint | Пример `LLM_MODEL` |
| --- | --- | --- |
| `groq` | Chat Completions, `https://api.groq.com/openai/v1/chat/completions` | `openai/gpt-oss-120b` |
| `deepseek` | Responses, `https://api.deepseek.com/responses` | `deepseek-flash` |
| `openai` | Responses, `https://api.openai.com/v1/responses` | `gpt-6.1-sol` |
| `anthropic` | Messages, `https://api.anthropic.com/v1/messages` | совместимая с JSON outputs модель Claude из вашего аккаунта |

Имена в таблице — примеры настройки, не проверенный доступ или рекомендация по
измеренному качеству. Для другой совместимой модели выбранного провайдера меняется
только `LLM_MODEL`; модель должна поддерживать используемую JSON Schema.

Groq Free — кандидат для публичного демо. Выбор `groq` сам по себе не делает
аккаунт бесплатным: до включения проверьте Free Plan и его фактические квоты.
При исчерпании квоты сохраняется явная ошибка; платного переключения нет.
Публичное размещение требует отдельной подготовки доступа, ограничения запросов
и изоляции посетителей: текущий один локальный demo-оператор не является такой средой.

Без `LLM_PROVIDER` используется `openai` для совместимости с прежними установками.
Непустые `LLM_MODEL` и `LLM_API_KEY` имеют приоритет над `OPENAI_MODEL` и
`OPENAI_API_KEY`. Старые переменные используются **только для OpenAI**: выбор Groq,
DeepSeek или Anthropic никогда не отправляет им старый OpenAI-ключ.
Заголовки `OPENAI_CUSTOM_HEADERS`, `OPENAI_ORG_ID` и `OPENAI_PROJECT_ID`
не передаются в Groq и DeepSeek.
Неизвестный провайдер отклоняется при чтении конфигурации. Произвольный endpoint
не настраивается; `OPENAI_BASE_URL` и другие SDK base URL не перенаправляют запрос.

Авторизация ChatGPT/Codex и подписки на чаты не используются. Не сохраняйте ключ
в репозитории, интерфейсе, shell history или материалах приёмки. Передавайте
`LLM_API_KEY` в окружение backend через свой менеджер секретов. Остальные настройки
для изолированной приёмки Groq в PowerShell:

```powershell
$env:PROOFLINE_PORT = '8002'
$env:APP_ORIGIN = 'http://127.0.0.1:8002'
$env:LLM_PROVIDER = 'groq'
$env:LLM_MODEL = 'openai/gpt-oss-120b'
$env:LIVE_ENABLED = 'true'
# LLM_API_KEY должен быть уже передан безопасно; значения ключей в команды не вставлять.
```

Все Compose-команды выполняйте с новым явным `-p proofline-live-acceptance`.
Не пересоздавайте основной `proofline` на 8000. Проект получает собственный том БД;
миграции/seed выполняются тем же [обычным путём](../README.md#run-the-local-demo).
После работы уберите временные переменные из текущего shell.

Compose передаёт эти переменные только приложению. После изменения окружения
пересоздайте app выбранного Compose-проекта; запуск контейнера сам по себе модель
не вызывает. Перед каждым live-прогоном согласуйте модель, условия и бюджет.
Историческое `gpt-5.6-sol` из Replay не является настройкой API-модели.

`MODEL_TIMEOUT_SECONDS=90` задаёт общий deadline запроса и сетевые timeout.
`MODEL_MAX_OUTPUT_TOKENS=4096` ограничивает вывод, включая reasoning-токены,
когда они учитываются провайдером. Обе настройки должны быть положительными.
Входные лимиты общие с Replay: текст не обрезается автоматически.

`GET /api/v1/capabilities` не обращается к провайдеру. `live_provider` и `live_model`
показывают выбор без ключа. `live_available=true` означает
только наличие явной конфигурации; `live_access_verified=false` сохраняет отличие
от live-приёмки. Отсутствующий ключ или модель не ломают replay readiness.
Ненастроенный `mode=live` возвращает 503 `LIVE_NOT_CONFIGURED` без создания run.

## Выполнить и проверить результат

В UI явно выберите «Live — новый вызов» и проверьте показанную модель.
HTTP-команда использует тот же маршрут и заголовок идемпотентности:

```json
{"mode": "live", "expected_case_version": 1}
```

`replay_id` для Live запрещён. На новый run выполняется один provider request:
SDK `max_retries=0`, без повторной генерации, polling, fallback, инструментов,
фонового выполнения и автоматического исправления ответа. HTTP redirects не
выполняются. Повтор того же ключа возвращает прежний run (202 во время выполнения,
200 после завершения). Только новая явная команда с новым ключом создаёт попытку.

Run сохраняет snapshot до запроса. Весь выбранный текст и каталог передаются
в одном JSON-входе; тексты исключённых источников в нём отсутствуют. Политика
считает обращение, контекст, метаданные и документы недоверенными данными.
Эталоны, recorded answers и исследовательский evaluator в запрос не входят.

`providers/live_profile.py` содержит утверждённый кандидат v3.2:
`proofline-policy-v3.2-candidate-1`, prompt
`proofline-responses-prompt-v2-candidate-1`. Он добавляет собственные доказательства
каждому событию, явное разделение отправки/получения и получение именно
недвусмысленного отказа перед сравнением с отменой. Это новый непроверенный
генерацией профиль. Исторические runs сохраняют исходные версии и хеши v3.1.
Схема строится из `AssemblyOutput`: для Responses передаётся как
`text.format=json_schema`, `strict=true`, для Groq Chat —
`response_format.json_schema` с `strict=true`, для Anthropic — `output_config.format`
с `type=json_schema`. Контракт, включая `minItems=1`, не ослабляется. Полученный
JSON всегда разбирается и проверяется приложением.

OpenAI/DeepSeek используют Responses-адаптер и официальный OpenAI SDK,
с явными профилями параметров. Только OpenAI получает `store=false` и
`truncation=disabled`; DeepSeek также не получает `background`, поскольку его API
не поддерживает эти параметры. DeepSeek документирует stateless-ответы и ошибку
при превышении контекста. У Groq поведение границы контекста требует live-проверки;
приложение само текст не сокращает. Различия параметров не включают повтор,
инструменты или переключение провайдера.

Groq использует отдельный Chat Completions adapter на том же SDK. Инструкция v3.2
передаётся одним system message, snapshot — одним user message; схема не меняется.
Фиксируются `api=chat_completions`, `request_profile=groq-chat_completions-v1`,
`n=1`, `stream=false`, `max_completion_tokens` из `MODEL_MAX_OUTPUT_TOKENS`.
Для совместимых моделей Groq можно задать `GROQ_REASONING_EFFORT=low`, `medium`
или `high` в окружении backend или в `.env` для Compose. При пустой или
отсутствующей настройке поле в запросе опускается, а профиль фиксирует
`reasoning_effort=provider-default`. Явное значение передаётся в запросе и
сохраняется в профиле `groq-chat_completions-effort-v1`. SHA256 запроса
учитывает это поле. Параметры sampling выбирает провайдер.
Поддержка effort и полной схемы зависит от модели.
Явное `GROQ_REASONING_EFFORT=none` доступно в отдельном профиле
`v3.3-citation-ids-test` для Qwen 3.8 27B.

### Отдельная проверка ограничений v3.3

Дополнительный файл `infrastructure/compose.groq-choices-test.yml` после
основного Compose-файла задаёт проект `proofline-groq-choices-test` с собственным
томом и loopback-портом 8012. Он выбирает `GROQ_PROMPT_PROFILE=v3.3-choices-test`
для Qwen `medium`. Live выключен по умолчанию. Для будущей согласованной проверки
у проекта отдельные переменные `PROOFLINE_CHOICES_LIVE_ENABLED` и
`PROOFLINE_CHOICES_GROQ_API_KEY`.

Доверенный список задаётся на backend в `PROOFLINE_CHOICES_LOOKUP_SOURCES`.
Например, для V01 подходит JSON `{"V01":["f9a88d5b726a4d4b"]}`, если оригинал
ответа исключён из снимка. Если он уже включён, модель сможет его цитировать,
но запросить его повторно нельзя. При пустом доверенном списке lookup-адресов нет.

В запросе профиль строит временную схему `assembly-choices-v1`. Модель заполняет
объект с запрошенными ключами фактов и выбирает действие с допустимым адресом.
Текст ответа сохраняется в `AnalysisRun.raw_output`. Код проверяет этот текст,
затем переводит факты из объекта в список в порядке запроса. Связанная
`ProposalRevision.body` остаётся в формате `assembly-output-v1`. Если ответ
нарушил временную схему, запуск сохраняет текст и ошибку без карточки.
Правила подтверждения остаются прежними.

Профиль записывает хеш временной схемы в `schema_sha256`, а хеш общей схемы
в `assembly_schema_sha256`. В новом архиве для каждого условия хранится точное
тело запроса в `request.json`. Verifier сверяет его хеш и отдельно проверяет
переход от исходного ответа к карточке. Прежние архивы используют свои шаблоны.
[Проверочные кейсы](proposals/2026-11-17-model-choices-prototype.md).

В [одиночном live-тесте V01](live-acceptance-qwen-choices-v01-2026-11-17.md)
Groq принял временную схему, а Qwen выбрал оригинал ответа клиента.

В [прогоне V02/V04 с ограничениями](live-acceptance-qwen-choices-v02-v04-2026-11-17.md)
V02 дал правильное следующее действие и полную хронологию, но был заблокирован

[Отдельная попытка V04 18 ноября](live-acceptance-qwen-choices-v04-2026-11-18.md)

Для профиля `v3.3-citation-ids-test` примените

Он задаёт отдельный проект на порту 8019. Live по умолчанию выключен.
Согласованный запуск использует `PROOFLINE_CITATION_IDS_LIVE_ENABLED` и

разметку отправки и получения. Неизвестный ID оставляет исходный ответ

события по времени UTC. Исходный ответ хранится в исходном порядке,
формулировки времени и цитаты сохраняются. При некорректной временной
метке её позиция сохраняется для диагностики. Преобразование отмечено
в метаданных запуска как `canonical_timeline_order=utc-v1`.
[Проверка архива](../scripts/verify_live_archive.py) сверяет каталог и
восстанавливает карточку по сохранённым ID.

[Результаты ограниченной live-проверки V01, V02 и V04](live-acceptance-groq-citation-ids-2026-11-18.md).

В этом профиле `PROOFLINE_CITATION_IDS_REQUIRED_EVENTS` может задавать
проверенные события по обращениям. Каждая запись содержит `event_type`,
`time` с ролью и исходным значением, `source_id`, `source_version_id`,
`text_sha256` и дословный `fragment` со временем. При проверке карточки
сверяются тип, роль и время каждого совпавшего события. Пропуск блокирует
одобрение с сохранением исходного ответа. Исключённая или устаревшая
версия источника не создаёт обязательного события. В экземпляре с такой
разметкой приложение также проверяет, что цитата о получении
не стала единственным подтверждением отправки. Инструкция для случая
с непрочитанным оригиналом показывает, как запросить его по адресу
и сохранить отдельную запись о получении.
Для размеченного снятия резерва инструкция различает банковские операции
`auth.open` и `auth.reverse`. Приложение блокирует снятие, если его время
подтверждает только строка открытия резерва из размеченного журнала.
[Контроль V06 с проверкой банковских операций](../evals/live/v23-groq-qwen-bank-operations-v06-2026-11-18/full-V06/review.json).

#### Вопросы и доказательства возврата в тестовом профиле

Для отдельного эксперимента с V02 и V03 передайте JSON из
[`groq-stage4-case-evidence.json`](../fixtures/live/groq-stage4-case-evidence.json)
в `PROOFLINE_CITATION_IDS_CASE_EVIDENCE` для тестового Compose либо в
`GROQ_TEST_CASE_EVIDENCE` при прямом запуске backend. Параметр по умолчанию
равен `null` и оставляет прежние запросы и проверки. Для кандидата Groq Free
отдельно задаются `PROOFLINE_CITATION_IDS_REASONING_EFFORT=none` и
`PROOFLINE_CITATION_IDS_MAX_OUTPUT_TOKENS=1000`. Live продолжает требовать
явного включения и ключа на закрытом стенде.

В этом же тестовом профиле V01 проверенная запись почтового шлюза может
указать на единственный доступный непрочитанный оригинал и дать дословную
цитату о получении письма. При неподтверждённом принятии декодер
предлагает открыть оригинал вместо просьбы прислать его. Он также
заполняет пустое действие, если карточка уже требует доказательства.
Решение открыть источник остаётся за оператором.
Для существующего события отправки предложения декодер может добавить
цитату, которую модель уже выбрала для факта. Событие должно ссылаться на
отметку отправки в том же письме, а время и роль должны совпасть.
Если письмо с предложением однозначно связано с проверенным журналом,
схема V01 требует хотя бы одно событие. Для отправки предложения в ней
разрешены два ID из письма, отметка отправки и текст самого предложения.
Повтор ID отклоняет декодер. Тестовая инструкция уточняет,
какая цитата относится ко времени отправки и какая к тексту предложения.

Отдельный режим `GROQ_TEST_ASSEMBLE_REVIEWED_EVIDENCE=true` доступен при
прямой настройке backend в тестовом профиле ID цитат. В V02 и V03 приложение
добавляет однозначно сопоставленные события из текущего снимка и исключает
эти типы из ответа модели. Для подтверждённого возврата приложение прикладывает
сверенные отправку, банковскую трассу и зачисление. Факты и следующий шаг
по-прежнему выбирает модель. Противоречие вывода о платеже выписке блокирует
одобрение. В V04 этот же режим при проверенной связи письма и журнала собирает
отправку предложения, отправку ответа и получение ответа. Строгий ответ модели
содержит только `facts`, `readiness` и `follow_up`. При пропуске источника или
некорректном порядке событий сохраняется полный формат. По умолчанию режим выключен.

В синтетическом V06 тот же режим сверяет снимок со всеми проверенными
источниками. Если модель правильно указала отмену и снятие резерва и привела
цитаты для обоих событий, приложение добавляет к факту оплаты цитату об
отсутствии списания и возврата. Если банковский документ был единственным
запросом, который оставался, карточка отмечается готовой к проверке правил.
При неполной или противоречивой записи запрос документа сохраняется. Исходный
ответ и решение оператора хранятся отдельно. На сохранённых ответах v51 все
шесть карточек прошли эталон после этой правки. Живой результат v51 по-прежнему
составляет пять проходов из шести. [Офлайн-тесты](../tests/unit/test_reviewed_evidence_assembly.py),
[исходный результат V06](../evals/live/v51-groq-gpt-oss-20b-stage4-acceptance-2026-11-25/full-V06/review.json).

После v53 в этом же тестовом режиме закреплены проверки по источникам.

- В V02 журнал подтверждает получение формы поддержки. Полный проверенный
  снимок подтверждает отсутствие исходного письма и отметки о его получении.
  Карточка оставляет время отказа неподтверждённым и запрашивает оба документа.
- В V05 приложение берёт время отправки из заголовка исходного письма, а время
  получения из отдельной записи поставщика. Эти события получают разные цитаты.
- В V06 приложение исключает событие списания, если оно опирается только на
  проверенную запись `auth.open` и остальные события совпадают с источниками.
  Проверка карточки блокирует списание, подтверждённое лишь открытием резерва.

Преобразования включаются для проверенных снимков. Отдельно проверены случай
с добавленным оригиналом отказа и журнал с реальным списанием. Исходные ответы
сохраняются отдельно. После преобразований обе сохранённые серии v51 и v53
дали 6/6 по замороженному эталону без вызовов Groq. [Регрессии](../tests/unit/test_reviewed_source_claims.py),
[результат живой серии v53](live-acceptance-stage-4-v06-release-2026-11-25.md).

После v54 в доказательство факта V05 добавляется дословный текст отказа из
проверенного письма. Приложение переносит цитату, когда вывод «отказ получен
до отмены» уже ссылается на отметку о получении этого письма и запись об отмене.
Валидатор требует текст отказа именно в доказательстве факта. На сохранённых
ответах v54 все шесть карточек прошли эталон офлайн. В живой серии v54 прошли
пять. [Тесты V05](../tests/unit/test_reviewed_source_claims.py),
[результат живой серии v54](live-acceptance-stage-4-source-claims-2026-11-25.md).

В эксперименте список вопросов в строгой схеме строится по запрошенным
фактам. Если ответ всё же содержит вопрос другой темы, карточка сохраняется
с блокирующим замечанием. Для размеченного возврата проверяются связь
журнала с выпиской, подтверждение зачисления и цитаты каждого из трёх
событий. Разметка относится к конкретным источникам и SHA256 их текста.
В синтетическом V03 при совпадении проверенных источников схема провайдера
задаёт `timeline.minItems=3`. Проверка карточки продолжает требовать три
конкретных события с нужными цитатами.
Если модель выбрала подтверждённую банковскую трассу для события зачисления,
декодер может связать её с фактом возврата, который уже ссылается на ту же
возвратную операцию и завершённое зачисление. Разметка активна только для
проверенных версий источников. В метаданных сохраняются правила,
по которым исходные ID преобразованы в карточку.
В метаданных есть суффиксы `case-evidence-v1` у профиля запроса и
`case-evidence-test-v1:<sha256>` у версии валидации. Исходные ID цитат
сохраняются в запуске, текст карточки — в отдельной версии предложения.
[Сохранённые проверки и границы эксперимента](proposals/2026-11-18-case-evidence-checks-offline.md).

Chat adapter принимает ровно один choice с assistant content и `finish_reason=stop`.
`length` означает `MODEL_OUTPUT_INCOMPLETE`, refusal/content filter — `MODEL_REFUSAL`;
tool calls, неизвестные причины и неверные формы не становятся карточкой.
Reasoning не подмешивается в JSON результата. Диагностический Chat envelope имеет
`raw_output_format=chat-completion-envelope`; raw и request ID сохраняются до
SDK-разбора. Автоматического переключения на Responses нет.

Anthropic использует отдельный native Messages-адаптер на существующем HTTPX,
API version `2026-10-21`, без новых библиотек, инструментов и HTTP-ретраев.
Для прямого вызова используйте ключ, привязанный к рабочей области Claude.
[Аутентификация Claude CLI и API](https://platform.claude.com/docs/en/manage-claude/authentication).
Отказ из `stop_reason` или `stop_details` и неполное завершение нормализуются в
те же коды. Некорректный envelope сохраняется как диагностика с известными IDs/usage.

Сохраняются провайдер, протокол, endpoint, версия профиля параметров (и API version
для Anthropic), запрошенная и возвращённая модель, ID ответа и request ID, если они
получены, версии и SHA256 политики/инструкции/схемы, SHA256 всего тела запроса,
deadline, output limit, latency, raw output, usage и безопасная ошибка.
`prompt_sha256` — хеш текста инструкции; полный вход связан через snapshot и
`request_sha256`. В `raw_output` хранится текст результата, в том числе частичный;
для отказа без текстового результата — JSON выходных элементов с отказом.
При неверной форме SDK-ответа сохраняется диагностический JSON envelope с
`raw_output_format=response-envelope`, а известные ID и usage остаются доступными.
Для не-JSON/необъектного HTTP 200 Responses сохраняются исходное тело и request ID
до SDK-разбора. Если провайдер вернул NUL, непарный surrogate или другой
недопустимый для JSONB metadata value, run завершается `INVALID_MODEL_OUTPUT`.
Полные исходные metadata, usage и raw сохраняются обратимо в экранированном
`raw_output` с `raw_output_format=provider-diagnostic`; небезопасное поле профиля
и небезопасный usage в JSONB заменяются на `null`, а безопасные поля сохраняются.
Каноническая карточка и результаты проверок хранятся отдельно.
Если исходный текст содержит символы, недопустимые для PostgreSQL text (NUL или
непарный surrogate), raw сохраняется обратимо как JSON-строка с
`raw_output_encoding=json-string`. Декодирование этой строки восстанавливает
исходный текст; это диагностическое представление, не исправленная карточка.

Usage сохраняется только полученным от API. При его отсутствии, в том числе при
timeout, значение `null`; нулевые расходы не предполагаются. Денежная стоимость
и тариф в этом адаптере всегда `null`: конфигурации датированного тарифа нет.
У Chat остаются native `prompt_tokens`/`completion_tokens`/`total_tokens` и полученные
details, без переименования в run или повторного прибавления reasoning tokens.
Текст HTTP-ошибок и исключений не сохраняется и не выводится: он может содержать
секреты или входные данные. Responses/Chat адаптеры сохраняют `provider_error_code`,
`provider_error_type` и `provider_error_param` только из закрытых allowlist.
Неизвестные значения и неверные типы остаются `null`; `error.message`, полное body
и `failed_generation` не копируются. Request ID связывает безопасную запись
с журналом провайдера. Groq HTTP 400 с `json_validate_failed` получает
`provider_error_stage=output_validation` и `INVALID_MODEL_OUTPUT`; обычный 400
остаётся `PROVIDER_REQUEST_REJECTED`. Это не включает повторную генерацию.

Если Groq Chat приложил к такому отказу разборчивый JSON-объект, приложение
добавляет `provider_output_field_diagnostics`. В нём только имена пропущенных
обязательных полей из отправленной схемы и число лишних полей верхнего уровня.
Тело ответа, его значения и имена неизвестных полей не сохраняются.
[Контроль V04](live-acceptance-stage-4-v04-field-diagnostic-2026-11-25.md).

`scripts/verify_live_archive.py` проверяет старые Responses archives по сохранённым
шаблонам. Для будущего `api=chat_completions` шаблон содержит два messages: system
с инструкцией и user с пустым `content=""`; verifier подставляет канонический
snapshot во второе сообщение и сверяет request/schema/prompt hashes. В отчёте
native Chat prompt/completion отображаются в общие input/output totals только
для известных счётчиков. Пропуски перечисляются в `usage_unknown_fields` и
`usage_unknown_for`; сумма известных значений не означает нулевой расход остальных.
Старые archives, manifests, usage и operator decisions не мигрируются.

| Код run | Причина |
| --- | --- |
| `MODEL_REFUSAL` | Отказ модели |
| `MODEL_OUTPUT_INCOMPLETE` | Неполный ответ, включая output limit |
| `INVALID_MODEL_OUTPUT` | Пустой/невалидный JSON, нарушение контракта или Groq 400 `json_validate_failed` |
| `MODEL_TIMEOUT` | Сетевой timeout либо общий deadline |
| `PROVIDER_ACCESS_DENIED` | HTTP 401/403 |
| `PROVIDER_PAYMENT_REQUIRED` | HTTP 402: баланс или необходимость оплаты |
| `PROVIDER_RATE_LIMITED` | HTTP 429, включая исчерпанную квоту |
| `PROVIDER_REQUEST_REJECTED` | HTTP 400/404/413/422: модель, схема или параметры |
| `PROVIDER_ERROR` | Связь, серверная или другая ошибка провайдера |

Failed run не создаёт новую карточку и не переключает режим. Разобранный ответ
с ошибками доказательств создаёт succeeded run и заблокированную карточку.
Поздний результат остаётся кандидатом при изменившейся Case.version. Прерванный
владелец и CAS обрабатываются тем же механизмом, что в Replay. Успешная проверка
всегда оставляет решение человеку: автоматического подтверждения нет.

## Отдельная live-приёмка

1. Согласовать API-доступ, конкретную модель, число запросов и допустимые расходы.
   Включить в бюджет проверку доступности/совместимости и ошибки; не начинать
   пробные вызовы до согласования.
2. Зафиксировать профиль, версию SDK/lockfile и параметры. На выбранном доступе
   проверить Structured Outputs и известные проблемные условия V02/V04, затем
   согласованный набор. Каждый новый run расходует максимум один request;
   повтор ключа не считается новой попыткой.
3. Сохранить новые результаты в отдельном версионированном каталоге evals, с
   моделью, условиями, usage, неизвестными величинами и ручным review. Отдельно
   оценить значения фактов, достаточность доказательств, полноту хронологии и
   следующий шаг. Не переносить метрику v3 7/9 на новую инструкцию.

Детерминированные тесты не доказывают качество модели, её доступность на аккаунте
или принятие схемы реальным API. Frozen baseline и записанные ответы неизменны.

# Саморевью Proofline перед публичным демо

Proofline решает исходную задачу подготовки операторского разбора в
границах учебного MVP. Оператор видит предложенные факты, события и
недостающие подтверждения, открывает исходное доказательство, исправляет
карточку и принимает решение по конкретной версии. Ценность решения
видна в том, что спорное утверждение можно проверить по источнику,
а исправление сохраняет историю. Для портфолио это адекватный сквозной
сценарий. Для внедрения в реальную поддержку ещё нужны один выбранный
процесс, независимая разметка и измерение времени ручной проверки.
[Исходная задача и границы](spec.md#цели-и-границы), [ограничения исследования](research.md#границы-доказательств).

## Что выдерживает проверку

| Слой | Оценка |
| --- | --- |
| Контракт и вход | Один типизированный запрос с выбранными текстами достаточен для малого синтетического кейса. Версия и хеш источника фиксируют, что именно увидела модель. Следующий шаг остаётся предложением оператору. |
| Модель и цитаты | Раздельные ответы «как вернула модель» и «как показано в карточке» дают проверяемую историю. Выбор ID устраняет опечатки при копировании цитат. Проверки времени, ролей и совместимости отмены, получения и снятия резерва закрывают конкретные наблюдавшиеся ошибки. |
| Данные и транзакции | Run, карточка, проверка и решение раздельны. Блокировка кейса, версия, ключ идемпотентности и сверка с владельцем запуска защищают от повторной генерации и перезаписи работы оператора поздним ответом. Один API-процесс соответствует объёму локального MVP. |
| Интерфейс | Три демонстрационные истории показывают доказательство, нехватку источника и исправление с сохранением старой версии. Видны Replay/Live, ошибки, история и явное решение человека. |
| Провайдеры | Смена модели и провайдера вынесена в настройки. OpenAI, DeepSeek, Groq и Anthropic покрыты офлайн-проверками адаптеров. Live-доказательства этого этапа собраны для Groq. |
| Измерения | Успешные, семантически неверные и технически отклонённые ответы сохранены. Принятие схемы, точность фактов, дословность, достаточность доказательств и полнота хронологии оцениваются раздельно. |

Сильнее всего решение в разделении исходных данных, предложения модели
и решения оператора. Главная слабость — разрыв между успешными отдельно
настроенными примерами и одним воспроизводимым экземпляром. Сценарная
сверка дала 6 проходящих карточек из выбранных архивов, 57 дословных
цитат и 29 260 токенов по этим шести ответам. [Результаты и решение по этапу 4](live-acceptance-stage-4-2026-11-18.md).

## Существенные замечания

**Блокирует публичный доступ.** Текущий API рассчитан на одного локального
оператора. Проверка Origin разрешает CLI-запросы без этого заголовка.
Она не определяет пользователя и право на кейс. При публикации
текущих эндпоинтов посетители получили бы общий доступ к кейсам,
истории и командам изменения. Решения в текущем MVP пишутся от
`demo_operator`. Открывать наружу следует отдельный экземпляр с
изоляцией посетителей. [Граница MVP](spec.md#лимиты-и-локальная-среда),
[Origin](../src/proofline/api/middleware.py#L26),
[команды API](../src/proofline/api/routes.py#L82),
[запись решения](../src/proofline/application/proposals.py#L175).

**Блокирует публичный Live на Free.** Идемпотентность и защита от
одновременного запуска работают в пределах кейса. У общего ключа Groq
пока нет серверного бюджета на минуту и день, предела активных вызовов
или управления сессиями посетителей. Лимиты размера ввода в символах
защищают приложение, а квота провайдера измеряется токенами. В опытах
паузы и квоту контролировала испытательная обвязка. Даже там получен
429 с видимым запасом в заголовках. Нужен общий лимитер перед сетевым
вызовом с учётом попыток, в том числе при неизвестном исходе.
[Граница запуска](../src/proofline/application/runs.py#L102),
[лимиты приложения](../src/proofline/config.py#L44),
[наблюдение 429](live-acceptance-groq-citation-ids-remaining-2026-11-18.md),
[квоты Groq](https://console.groq.com/docs/rate-limits).

**Важно для приёмки и упаковки.** Флаг другого кейса может менять
инструкцию текущего, поскольку выбор подсказки смотрит на настройки
всего экземпляра. Кроме того, перенос проверенной разметки на свежую БД
требует перепривязки ID версии. Я проверил этот край офлайн на V02.
С совпавшими версиями пустая хронология блокируется. При тех же
текстах и новых ID версий все три привязки выпадают и пустая хронология
доходит до оператора. Нужны выбор по снимку, переносимая привязка
по ID источника и хешу и видимый результат проверки разметки при запуске.
[Выбор инструкции](../src/proofline/providers/live.py#L82),
[привязка](../src/proofline/config.py#L72),
[seed](../src/proofline/application/seed.py#L32).

**Важно для доверия к карточке.** Точная цитата и правильный тип поля
ещё оставляют проверку смысла. В офлайн-копию принятого V06 я добавил
снятие резерва в 16:40 с цитатой об отмене, сохранив настоящее снятие
в 16:43. Текущий валидатор не выдал замечаний. Проверка подтверждает
время в цитате, а правила для размеченных событий проверяют наличие
известных записей и несколько конкретных подмен. Совпадение типа, роли и
времени размеченного события само по себе не требует ссылки на
размеченный фрагмент. Для банковских событий стоит проверять связку
«тип операции, время, источник» по фактической строке журнала. Для
остального смысла нужен оператор. Дальнейшее качество
измеряйте на новых примерах, включая неоднозначные и конфликтующие
источники. [Валидатор](../src/proofline/validation/assembly.py#L99),
[правила хронологии](../src/proofline/validation/required_events.py#L21).

**Важно для изоляции провайдеров.** Установленный OpenAI SDK 2.54.0
читает `OPENAI_ORG_ID`, `OPENAI_PROJECT_ID` и
`OPENAI_CUSTOM_HEADERS` из окружения даже при явном ключе и другом
адресе API. В офлайн-проверке с подставными значениями и in-memory
HTTP-транспортом Groq и DeepSeek получили заголовки OpenAI, а подставной
Authorization перекрыл настроенный ключ адаптера. Оба клиента должны
формировать разрешённый набор заголовков для своего адресата.
Это нужно закрепить тестами с загрязнённым окружением.
[Клиент Groq](../src/proofline/providers/groq_chat.py#L157),
[клиент Responses](../src/proofline/providers/openai_responses.py#L90),
[зафиксированная версия SDK](../uv.lock).

**Граница переносимости.** ID цитат, сортировка и дополнительные
проверки размеченных событий сейчас относятся к тестовому Groq-профилю.
Общая карточка и операторский путь переносимы. При смене провайдера
используется другой модельный контракт, поэтому для него нужна своя
приёмка. Глубину абстракции сейчас считаю достаточной. Полезнее стабилизировать
один путь и использовать общие типы, сохраняя явные различия протоколов.
[Фабрика адаптеров](../src/proofline/providers/factory.py#L12),
[декодирование ID](../src/proofline/providers/model_choices.py#L75).

**Размер и пригодность контекста.** Каталог ID построен из уникальных
строк. Для небольших синтетических источников он достаточен. Длинный
журнал увеличивает одновременно вход и перечисление допустимых ID в
схеме. Повторяющиеся строки остаются доступным для чтения контекстом.
Для длинного входа нужна оценка допустимого объёма и качества отбора
цитат на новых данных. [Каталог цитат](../src/proofline/providers/citation_ids.py#L82).

## До публичного демо

1. **Воспроизвести один кандидат.** Выбирать ветку инструкции по снимку
   кейса, привязывать проверенные события при подготовке seed, зафиксировать
   настройки и повторить V01–V06 на одном собранном экземпляре. Проверить
   неизменность Replay и сохранение исходного ответа отдельно от карточки.
2. **Изолировать посетителей и источник данных.** Поднять отдельную БД и
   отдельный доступ к Groq. Дать посетителю набор готовых синтетических
   кейсов и свою песочницу для запусков и правок. На первом публичном
   релизе ограничить вход синтетическими примерами. Сервер отправляет
   выбранный текст провайдеру, а истории остаются в БД приложения.
   [Контроль данных Groq](https://console.groq.com/docs/your-data).
3. **Ограничить Live на сервере.** Сохранить ключ на backend, проверить
   принадлежность к Free, резервировать минутный и дневной бюджет до
   обращения к API и ограничить параллельность. При 429 показать причину
   и доступный путь в Replay. Числа 30 запросов в минуту, 1000 в день,
   8000 токенов в минуту и 200 000 в день проверялись для Qwen в
   Groq Console. Это входные границы для проектирования, а не обещание
   доступности. [Лимиты Groq](https://console.groq.com/docs/rate-limits).
4. **Проверить эксплуатацию.** Собрать зафиксированную версию из чистого
   Git-чек-аута, выбрать лицензию и оформить README с измеренными
   ограничениями. На отдельном стенде проверить HTTPS, таймауты,
   восстановление, конкурентные запросы, исчерпание квоты и отсутствие
   доступа к чужой истории. Для первого запуска достаточно одного API-процесса
   и PostgreSQL. [Границы одного процесса](api.md#версии-и-конфликты).

Публичный путь имеет смысл делать небольшим. На нём посетитель увидит
живой разбор одного синтетического кейса с цитатами и сохранённой
версией. Полноценная интеграция с тикетами, самостоятельное выполнение
действий и масштабирование базы идут за пределами этого результата.

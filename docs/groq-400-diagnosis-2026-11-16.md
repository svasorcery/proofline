# Groq HTTP 400: причина и предложение исправлений

16 ноября 2026 года. Разбор без новых inference-вызовов. Действующие source,
prompt/policy, схема, настройки контейнеров, БД и решения оператора не изменялись.
Это дополнение к [первичной приёмке](live-acceptance-2026-11-16.md), а не новый прогон.

## Установленная причина

В Groq Console → Dashboard → Logs → Show Errors Only найдена запись V05:

| Поле | Значение |
| --- | --- |
| Request ID в локальном run | `req_01m7jr4a38e8xt58skwactap6m` |
| ID, показанный в консоли | `req_0...ap6m` |
| Время запроса | 16.11.2026 20:57:54 Europe/Moscow, совпадает с локальным 17:57:54 UTC |
| Модель | `openai/gpt-oss-120b` |
| HTTP | 400 |
| **Код Groq** | **`json_validate_failed`** |
| Input / output tokens в журнале | 2,460 / 2,383 |
| TTFT / latency провайдера | 0.37107 / 5.39517 s |

Совпадают время, модель, имя приёмочного API-ключа и суффикс request ID; в журнале
проекта одна ошибка. [Сохранённое наблюдение](../evals/diagnostics/groq-400-2026-11-16/provider-console-observation.json)
не содержит ключа или сведений профиля пользователя.

**Запрос дошёл до генерации. Groq отклонил полученный результат на этапе
JSON/schema-валидации.** Для best-effort Structured Outputs Groq отдельно описывает
HTTP 400 при несоответствии сгенерированного JSON схеме:
[официальная документация](https://console.groq.com/docs/structured-outputs#error-handling).

Точный повреждённый JSON и нарушенное ограничение схемы или путь поля в доступном журнале
не показаны, а локальный адаптер их не сохранил. Нельзя доказательно утверждать,
что отсутствовало конкретное поле, был неправильный enum, синтаксис или другое
нарушение. Код ошибки устанавливает стадию отказа, а не конкретную строку JSON.

## Что проверено отдельно

- Локальное JSON-тело V05 корректно восстанавливается из сохранённого snapshot
  и шаблона; SHA256 совпадает с отправленным `request_sha256`.
- Схема, модель и параметры одинаковы во всех пяти попытках. Четыре предыдущих
  запроса дали структурно допустимые карточки.
- V05: 11,037 UTF-8 bytes полного request body, четыре источника, те же два
  requested_fact_keys, что у V02. Только входной snapshot отличается.
- Между началами соседних запросов было 81–107 секунд; сервер сообщил конкретный
  `json_validate_failed`, а не rate-limit error.
- Провайдер сообщил 2,383 output tokens при лимите 4,096. Оснований лечить этот
  случай простым увеличением output limit нет.

Наличие `text.format.strict=true` в нашем request body подтверждено. **Это само
по себе не доказывает constrained decoding на стороне Groq Responses.** В
[Responses-примере](https://console.groq.com/docs/responses-api#structured-outputs)
показан `text.format=json_schema`; наиболее явные гарантии и примеры strict mode
даны для `chat.completions` с `response_format.json_schema.strict=true`.
Документация и один код ошибки не позволяют заключить, что Responses всегда
игнорирует strict. Такая совместимость остаётся отдельным вопросом к провайдеру.

## Почему приложение показало другую причину

В `providers/openai_responses.py` обработчик `APIStatusError` сохраняет request ID
и HTTP status, затем классифицирует ошибку только по статусу через
`http_error_code(400)`. Так `json_validate_failed` превращается в общее
`PROVIDER_REQUEST_REJECTED`. Полезные структурированные поля SDK `exc.code`,
`exc.type` и `exc.param` теряются вместе с небезопасным текстом исключения.

Это воспроизведено одним **in-memory HTTP** ответом, без внешнего запроса:
[offline probe](../evals/diagnostics/groq-400-2026-11-16/offline-diagnostic-probe.json).
SDK 2.54.0 уже предоставляет error.code; новый SDK для исправления не требуется.

## Предлагаемые изменения адаптера

Первым небольшим изменением:

1. Для Groq распознавать известный `json_validate_failed` как
   `INVALID_MODEL_OUTPUT`, сохраняя `http_status=400`, request ID,
   `provider_error_code=json_validate_failed` и `provider_error_stage=output_validation`.
   Общий 400 без такого кода остаётся `PROVIDER_REQUEST_REJECTED`.
2. Сохранять только типизированные идентификаторы из закрытых allowlist:
   известные error codes/types и известные пути параметров. Не копировать
   произвольную строку `param` или `type`, даже если SDK аннотирует её как string.
   Неизвестные/неправильно типизированные значения остаются `null`.
3. Не сохранять exception string, `error.message`, весь error body и
   `failed_generation`. Эти поля могут отражать вход или секреты. Диагностическая
   классификация не должна увеличивать утечку данных.
4. Сохранить один запрос на run, `max_retries=0`, прежнюю идемпотентность и
   остановку. Автоматическая повторная генерация не является исправлением.

Это исправляет точность диагностики; устойчивость самой генерации требует
отдельной проверки. Контракт, `strict=true` и evidence constraints сохраняются.

Не предлагаю сразу переводить все три провайдера на другой протокол. Если Groq
не подтверждает strict для Responses, отдельный Groq Chat Completions профиль
с документированным strict mode — обоснованный следующий вариант. Внешние
`LLM_PROVIDER`/`LLM_MODEL` настройки и общий операторский workflow сохранятся;
OpenAI и DeepSeek могут остаться на Responses. Такой переход нужно объявить и
измерить отдельно, а не включать как скрытый fallback.

Проверки для будущего патча: известный code vs обычный 400, подставленные секреты
в message/failed_generation/type/param, неожиданные типы, сохранение request ID,
один вызов, PostgreSQL failed run и повтор того же ключа. Всё это проверяется
offline. Сейчас патч не внесён: автор запросил разбор и предложение.

## Как изменить инструкцию

[Полный кандидат v3.2](proposals/2026-11-16-live-policy-v3.2-candidate.txt)
подготовлен отдельно. В модель передаётся только текст между BEGIN/END MODEL
INSTRUCTIONS, без служебного заголовка предложения. Активный v3.1 не менялся;
кандидат не проходил генерацию и не имеет новой метрики качества.

| Наблюдение | Изменение кандидата |
| --- | --- |
| V02: получение формы выдано за получение отказа | Сначала доказать содержание недвусмысленного отказа и получение именно этого сообщения, затем сравнивать с выполненной отменой. Разделить заявление о якобы отправленном ранее отказе и новый явный отказ в тексте самой формы. |
| V04: inbound 12:27 назван sent | Явная таблица: Date/Sent → customer_replied/sent; inbound/Received → received. Показать оба известных момента даже при unconfirmed бизнес-факте. |
| V01: факт процитирован правильно, событие использует только журнал доставки | Ввести field-local proof: у каждого события собственные смысловые фрагменты и время; цитаты из другого поля не наследуются. Для принятия альтернативы нужны содержание согласия и получение связанного сообщения. |
| V03: время есть в документе, но отсутствует в цитате события | Проверить дословное time.value именно в evidence этого события. Если документ уже включён, исправить выбор фрагмента внутри ответа. |
| Ложный ready_for_rules | Выбирать readiness после проверки полной цепочки доказательств каждого запрошенного факта. Правдоподобного значения недостаточно. |

Важная граница для V02: не вводить правило «любая форма не является отказом».
Форма с собственным недвусмысленным отказом и временем приёма может быть валидным
новым отказом. Именно содержание и связь с получением определяют значение.
Кандидат сохраняет это различие и использует общий контрпример, без case IDs,
дат из набора, готовых ответов или reference JSON.

`time_not_in_fragments` уже реализован и сработал на V03; его не нужно писать
заново. Смысловую достаточность V02/V01 и полноту V04 текущие validators не
доказывают. Не следует добавлять ветки по V02/V04 или regex, который объявляет
все формы неподтверждёнными. Граница ручного review сохраняется.

Кандидат длиннее текущего текста: при будущем запуске нужно проверить лимит
входных токенов Free Plan. Дополнительные модельные проходы, self-repair-запросы
и цепочки инструментов не предлагаются: остаётся один вызов с итоговым JSON.

## Как проверить улучшение позже

Новый профиль и новый каталог результатов с отдельно согласованным бюджетом.
Сохранить первоначальный v1 полностью. Помимо исходных условий нужны пары:
заявление о более раннем отказе / собственный явный отказ; два времени сообщения;
содержание согласия отсутствует / присутствует; время процитировано у соседнего
поля / у самого события; совпадающая / чужая платёжная трасса. Это уменьшит
подгонку к четырём уже увиденным ошибкам. Не объявлять улучшение по проверке
текста инструкции: доказательством станут новые ответы и отдельный review.

## Дополнение к usage

Run V05 по-прежнему содержит `usage=null`, как было получено приложением.
Консоль провайдера отдельно сообщает 2,460 input + 2,383 output = 4,843 tokens.
С учётом ранее известных 16,297 это **21,140 tokens по двум источникам**:
API для четырёх успешных ответов и Console для ошибочного. Reasoning breakdown
пятой попытки неизвестен. Это не новая генерация и не изменение старой записи.
Денежный расход через API не установлен; источник Free Plan — подтверждение автора.

В этом разборе новых inference-вызовов — **0**. Основные и приёмочные контейнеры
не перезапускались, SQL/HTTP-команды изменения БД не выполнялись, ключ не читался.

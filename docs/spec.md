# Спецификация Proofline

Версия 1.1 от 9 ноября 2026 года. Организация материалов обновлена 9 ноября 2026 года; продуктовые требования сохранены. Имя нового репозитория — `proofline`. Это спецификация реализации первого учебного MVP Proofline. Начинать разработку в отдельном репозитории; Git-история авторского workspace ему не нужна.

Продукт помогает оператору подготовить и проверить разбор обращения: факты, доказательства, хронологию и недостающие подтверждения. Основной путь — полный доступный контекст, один вызов модели, проверки кода, затем решение человека. Система не разрешает и не выполняет возврат денег.

## Цели и границы

MVP должен дать практику структурированного извлечения, проектирования контекста, проверяемых доказательств, evals и включения AI в операторский процесс. Для портфолио он должен показывать понятный сквозной сценарий, ошибки модели и их обработку, воспроизводимый запуск и обоснованные инженерные решения.

Автор имеет 12 лет опыта .NET/backend/распределённых систем; цель — углубиться в бизнес AI-автоматизации и показать навыки в самостоятельном GitHub-демо после Travel Agency. Широкий коммерческий запуск не является целью. Название Proofline, имя репозитория и Python-пакета `proofline` выбраны окончательно. Совпадения с другими проектами осознанно приняты для личного демо; подбор имени не возобновлять.

| Входит в MVP | Остается за его границей |
| --- | --- |
| Шесть синтетических travel-кейсов и три варианта с исключенным источником | Реальные клиентские данные и юридическая оценка претензий |
| Ввод учебного обращения и текстовых источников, выбор источников анализа | PDF/OCR, почтовые подключения и автоматическая загрузка документов |
| Полный контекст, replay и один явно настроенный live-адаптер | Автономные агенты, несколько моделей в одном workflow и автоматический fallback |
| Факты, отдельные доказательства, временные роли и следующий шаг | Финансовые расчеты модели, выполнение платежей и отправка сообщений клиенту |
| Исправление, подтверждение или отклонение разбора оператором | Система тикетов, SLA, полноценный SaaS и мультитенантность |
| Один backend, одна БД, небольшой интерфейс | Микросервисы, plugin platform, брокер, распределенная очередь |

MCP, LangGraph, advanced retrieval, reranking, gateway и расширенная наблюдаемость сохраняются в учебной программе. Их исследования не являются зависимостями первого работающего пути.

Исследования выполнены на небольших синтетических наборах с AI-эталонами. Проверки специалистом реального процесса и подтвержденного ROI нет. В наборе представлены разные travel-контексты, в том числе размещение; перед бизнес-внедрением выбирается один конкретный процесс и проверяются его источники.

## Зафиксированные решения

| Область | Решение |
| --- | --- |
| Backend | Python 3.12+, FastAPI, Pydantic v2, uv, ruff, pytest, один type checker |
| Данные | PostgreSQL, SQLAlchemy 2, Alembic; обычные таблицы и JSONB для версионированных документов |
| UI | React, TypeScript, Vite; два основных экрана, без SSR |
| Размещение | Docker Compose: приложение и PostgreSQL. Собранный UI обслуживается приложением с одного origin |
| Среда MVP | Один API-процесс, один локальный демонстрационный оператор, привязка порта к loopback |
| Анализ | Весь выбранный текстовый контекст в одном запросе; только типизированный результат |
| Live-провайдер | Первый адаптер — OpenAI Responses API со Structured Outputs, через официальный Python SDK |
| Режим по умолчанию | Replay; живой вызов включается явно и требует отдельно настроенного API-доступа |
| Область UI | Русский интерфейс; английские имена API, модулей и README нового публичного репозитория |

Конкретные совместимые версии библиотек и образов фиксируются при bootstrap в lock-файлах и конфигурации сборки. Установка самой новой версии не является целью. Разумный выбор CSS-библиотеки и UI-компонентов остается исполнителю; отдельная дизайн-система не требуется.

API-модель задается конфигурацией и проверяется на доступность перед live-приемкой. Имена моделей из исторического Codex CLI не считаются автоматически доступными именами API. Авторизация ChatGPT/Codex не копируется в сервер и не подменяет API-ключ.

Structured Outputs используются для формы ответа, но не доказывают истинность содержания. Нужно отдельно обрабатывать отказ модели и неполный ответ, затем валидировать результат приложением. Основание для интерфейса адаптера: [официальное руководство OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs).

## Основание и оставшиеся ограничения

Измеренная регрессия v3 дала 7/9 полных прохождений, 72/72 дословных фрагмента и 13/13 правильных значений запрошенных фактов. В V02 пропущено обязательное по эталону событие отправки формы. В V04 условное согласие сосуществовало с событием принятия альтернативы, а следующий шаг перечитывал уже выданный журнал.

В seed есть отдельный `approval_gate.py`, блокирующий противоречие и бесполезное повторное чтение снимка. Исправленная `policy_v3_1_unmeasured.json` восстановила определения, но еще не проходила отдельный модельный прогон. Это кандидат для live-пути, а не подтвержденная новая метрика качества.

При переносе в приложение сохранить явные определения: `alternative_accepted` означает только получение безусловного согласия; без нового доступного источника нужен запрос подтверждения; снимок не обновляется повторным чтением. Уточнить правило полноты хронологии: для подтвержденного клиентского сообщения показывать отправку и получение раздельно, когда оба момента известны. Заявление о более раннем письме не создает событие раннего отказа.

Воспроизводимая база v3 сохраняется в `evals/baselines/v3/`, синтетические кейсы и записи — в `fixtures/`. Эти результаты неизменяемы. Для переноса модулей в приложение их нужно копировать и адаптировать, а не править измеренную версию. Новые evals получают свою версию и каталог результатов. Полный исходный пакет и история переноса хранятся локально в игнорируемой `notes/`; работа проекта от них не зависит.

## Пользовательский путь

### Список обращений

Оператор видит название, статус актуального разбора, наличие выполняющегося анализа и время последнего изменения. Доступны фильтры по статусу и открытие карточки. Начальные примеры V01–V06 загружаются детерминированным seed.

Можно создать учебное обращение: текст и список проверяемых фактов из поддерживаемого каталога. Можно добавить источник текстом, изменить его метаданные или создать новую версию текста. Загрузка файлов, OCR и переходы по внешним URL не реализуются.

### Карточка обращения

Карточка содержит исходное обращение и источники, разбор с фактами/хронологией, панель проверки и историю версий. На широком экране разбор и открытый источник видны одновременно; на узком панели переключаются, сохраняя выбранный фрагмент.

Действия оператора:

1. Выбрать включенные в анализ источники. Невключенный или пока не полученный источник остается видимым в каталоге, но не передается модели.
2. Выбрать replay либо live. Replay показывает конкретную сохраненную запись и дату; live — выбранную модель и факт нового вызова.
3. Запустить анализ и получить карточку либо явную ошибку.
4. Открыть доказательство: UI показывает именно ту версию источника, на которой основан разбор, и выделяет каждый фрагмент отдельно.
5. Исправить значение факта, событие, роль времени, доказательство или список запрашиваемых подтверждений.
6. Сохранить новую версию, проверить замечания, подтвердить либо отклонить разбор с комментарием.

Кнопка называется «Подтвердить разбор», а не «Одобрить возврат». Она подтверждает результат проверки человеком. `ready_for_rules` из ответа модели отображается как ее предложение о готовности данных и не заменяет операторское решение.

Тексты источников отображаются как обычный текст, без исполнения HTML. Сообщения проверок должны объяснять действие: «Фрагмент не найден в этой версии источника», «Условное согласие нельзя отметить как принятую альтернативу». Технические версии и raw JSON доступны в раскрываемых деталях запуска, а не загромождают основной рабочий путь.

### Ошибки и неполные данные

При невалидных доказательствах и противоречиях подтверждение заблокировано; карточка остается доступной для исправления. Неизвестный факт хранится как `unconfirmed`. Полнота требований проверяется на учебных кейсах evals и в текущем обращении оператором; сам по себе непустой список не гарантирует полноту смысла.

Если live недоступен или завершился ошибкой, UI показывает это. Автоматического перехода к replay нет. Вопросы из `follow_up` можно просмотреть и скопировать; кнопки отправки и реальные вызовы предложенных инструментов в MVP отсутствуют.

## Модель данных и версии

Бизнес-идентификаторы — серверные строки. Seed сохраняет case_id `V01`–`V06` и существующие source_id, чтобы replay не требовал переписывать ответы. Новые обращения получают UUID в строковой форме. Source_id уникален внутри обращения; доступ к источникам всегда ограничен case_id.

| Сущность | Обязательные данные и смысл |
| --- | --- |
| `Case` | id, title, user_text, requested_fact_keys, справочные money/context, `content_revision`, `version`, `current_proposal_revision_id`, timestamps |
| `Source` | case_id, source_id, kind, locator, title, trust label, position, included, current_version_id; источник может быть зарегистрирован без текста |
| `SourceVersion` | неизменяемые id, source_id, sequence, text, text_sha256, created_at |
| `AnalysisRun` | id, case_id, mode, idempotency_key, request_hash, input snapshot/digest, content_revision, base_case_version, owner_instance_id, status, generation profile, raw output/usage/error, timestamps |
| `ProposalRevision` | id, case_id, analysis_run_id либо null, parent_revision_id, origin, content_revision, input digest, source-version bindings, canonical body, body_sha256, created_at |
| `ValidationCheck` | неизменяемые id, proposal_revision_id, validation profile/version, issues, resolved spans, result, created_at |
| `ReviewDecision` | неизменяемые id, proposal_revision_id, body hash, source bindings digest, validation_check_id, kind, actor, reason, timestamp |

`Case.content_revision` увеличивается при изменении входа: текста обращения, проверяемых фактов, справочного контекста, состава/порядка источников или выбранных версий. `Case.version` увеличивается при любом изменении агрегата, включая правку/активацию разбора и операторское решение. Он используется для optimistic concurrency.

Создание AnalysisRun и изменения его статуса сами по себе не увеличивают Case.version: это отдельная запись. При создании run под блокировкой Case фиксируется base_case_version. Автоматическая активация нового результата при совпадении этой версии увеличивает ее; иначе сохраняется только новый кандидат. Это не позволяет анализу инвалидировать собственный optimistic check.

Текст нового `SourceVersion` один раз нормализуется по переносам строк: CRLF/CR → LF. Остальные пробелы и Unicode не преобразуются. SHA256 вычисляется по UTF-8 сохраненного текста. После создания версия неизменяема.

Model output содержит source_id. Сервер связывает его с конкретным SourceVersion из снимка запуска; модель не выбирает доверенную версию. Новая версия источника не меняет старые доказательства. Она делает прежнее одобрение неприменимым к текущему состоянию обращения.

В input snapshot сохраняются также все переданные метаданные: kind, locator, title, trust, порядок и состав каталога, user_text, requested_fact_keys и справочный контекст. Историческая проверка и UI используют именно этот snapshot, а не текущие изменяемые поля Source. Операторская дочерняя версия наследует тот же снимок. Текущие поля Case/Source используются отдельно для определения stale и допуска к подтверждению.

`ProposalRevision.body` неизменяем. Любая правка создает дочернюю версию с origin=`operator`; исходный ответ модели и история остаются доступны. При правке в той же content_revision привязки источников сохраняются. Если вход обращения изменился, старую карточку можно только просматривать; для текущего входа запускается новый анализ. Первый MVP не поддерживает молчаливую перепривязку старого разбора к новым источникам.

Историческое операторское решение не удаляется при изменении входа или создании новой версии. На каждую версию разбора допускается одно финальное решение; для пересмотра создается новая версия. Последнее решение считается актуальным только для активной версии, текущего входа и действующей версии проверок.

## Контракт разбора

Каноническая JSON Schema находится в [contracts/assembly-output.schema.json](../contracts/assembly-output.schema.json). Это один объект `AssemblyOutput`, без транспортной обертки `results`. В приложении схема генерируется из Pydantic-моделей и сверяется с экспортируемым контрактом; TS-типы клиента выводятся из OpenAPI или общей генерации, а не поддерживаются вручную в расходящихся копиях.

```text
AssemblyOutput
  case_id
  facts[]
    key, value
    evidence[]: source_id, fragments[]
  timeline[]
    event_type
    time: value (исходный ISO8601 с offset), role
    evidence[]: source_id, fragments[]
  readiness
  follow_up: action, locator | null, requirements[]
```

Разрешены только заданные поля. Типизация строгая; строка не становится числом и неизвестное значение enum не исправляется автоматически. `time.value` остается строкой источника; UTC instant вычисляется отдельно и не заменяет ее.

| Ключ факта | Допустимые значения |
| --- | --- |
| `alternative_acceptance` | confirmed, conditional, not_accepted, unconfirmed |
| `payment_outcome` | refund_settled, refund_pending, authorization_release, unconfirmed |
| `withdrawal_timing` | before_supplier_cancel, after_supplier_cancel, unconfirmed |
| `cancellation_status` | confirmed, unconfirmed |

Ключи фактов ответа должны точно совпадать с requested_fact_keys обращения, без дубликатов. Для установленного факта нужны доказательства; `unconfirmed` не означает, что событие не происходило.

| Тип события | Роль времени |
| --- | --- |
| alternative_offered, customer_replied | sent |
| customer_message_received, alternative_accepted, customer_withdrawal | received |
| payment_captured, refund_initiated, refund_settled, authorization_released, supplier_cancelled | occurred |

`alternative_accepted` разрешено только при явном `alternative_acceptance=confirmed`. Получение сообщения с условным согласием отображается как получение сообщения, а не как безусловное принятие альтернативы. Для `withdrawal_timing` сравниваются получение недвусмысленного отказа и фактическая отмена, а не время черновика/экспорта.

Разрешенные requirements: `original_customer_message`, `delivery_receipt`, `quiet_room`, `courtyard_windows`, `original_acceptance_reply`, `bank_settlement_document`. Их стабильные русские тексты перенести из `evals/baselines/v3/contract.py`. Код формирует отдельный пункт для каждого выбранного требования, не дописывая пропущенное по эталону.

`readiness` принимает `ready_for_rules`, `request_evidence`, `human_review`. Для request_evidence нужен конкретный follow_up. Для none locator=null и requirements пусты; для ask_user locator=null и список непуст. Для read_source/query_provider/query_payment нужен видимый разрешенный locator нужного типа.

Следующий шаг является предложением оператору. Приложение его не исполняет. Locator принадлежит каталогу текущего обращения; произвольные URL, пути файлов и новые полномочия из текста не принимаются.

## Доказательства и проверки

Каждый fragment — непустая непрерывная дословная подстрока связанной версии source.text. Не найденный либо неоднозначно найденный фрагмент блокирует подтверждение. Для неоднозначной короткой цитаты оператор выбирает более длинный фрагмент с контекстом.

Сервер вычисляет `[start_cp, end_cp)` в Unicode code points и source_sha256. UI получает точные границы и версию, не вычисляет доверенные смещения из результата модели. JavaScript использует UTF-16, поэтому для подсветки нужна явная конверсия либо работа с массивом code points. Обязателен тест с emoji перед выделенным фрагментом.

Валидатор не склеивает фрагменты в новую «цитату». Для offline-eval их интервалы одного source_id могут вместе покрывать anchor; непокрытые слова, включая отрицание, остаются непокрытыми. Разные источники не подменяют друг друга. AND/OR-наборы доказательств и альтернативы — функция эталонов eval, не runtime-догадки.

В приложении выполняются три уровня:

1. **Runtime-структура:** схема, источник/версия, буквальность и однозначность, временная зона, роль, порядок и дубликаты событий, допустимость действия и locator.
2. **Проверки согласованности:** принятие альтернативы требует confirmed; неизвестные/условные факты не могут быть ready_for_rules; request_evidence требует следующего шага; повторное чтение уже выданного снимка не является новым подтверждением. Refresh в MVP отсутствует.
3. **Человек:** проверка смысловой достаточности, полноты событий и условий. Успешные уровни 1–2 всегда оставляют `needs_operator_review`.

Денежные значения выводятся из integer amount_minor, currency=USD и scale=2. Значение 12000 отображается как 120.00 USD. Модель не вычисляет и не форматирует итоговую сумму; карточка помечает ее как справочный контекст, а не размер одобренного возврата.

Эталоны, expected answers и evaluator не передаются модели и не используются приложением для заполнения результата. Runtime-валидатор не должен импортировать `reference_v3.json` или выбирать ветки по известному case_id.

## Состояния и одобрение

`AnalysisRun.status`: running → succeeded либо failed. Полученный и разобранный по схеме ответ с ошибками доказательств — succeeded run и заблокированная карточка. Невалидный JSON/неразобранная схема/refusal/timeout — failed run без канонической новой карточки. Raw output и диагностическая причина сохраняются отдельно.

Для карточки сервер возвращает независимые признаки: активность, stale по входу, актуальность ValidationCheck, blocking issues и ReviewDecision. UI-статус вычисляется из них; поле модели readiness для этого не используется.

Подтверждение выполняется в транзакции с блокировкой Case:

- expected case.version совпадает;
- выбрана активная ProposalRevision, ее body hash и content_revision актуальны;
- source-version bindings совпадают с текущим выбранным набором;
- сервер повторно запускает текущую версию проверок и сохраняет ValidationCheck;
- блокирующих ошибок нет и нет финального решения по этой версии;
- ReviewDecision фиксирует конкретные хеши, проверку, оператора и комментарий; Case.version увеличивается.

Смена версии правил проверки делает старое решение историческим: для актуального одобрения нужна проверка и решение по текущему validation profile. В UI это состояние «Требуется повторная проверка», а не автоматическое сохранение прежнего разрешения.

Отклонение разрешено и для заблокированной карточки; нужен комментарий. Повтор одного и того же запроса решения возвращает прежний результат. Попытка принять другое финальное решение по той же версии возвращает конфликт; оператор создает новую версию для пересмотра.

Результат модели не должен затирать работу оператора. Run сохраняет base_case_version. При завершении его карточка активируется автоматически только если версия агрегата не изменилась. Иначе новый результат остается отдельным кандидатом в истории. Активация кандидата — явное действие с проверкой текущей версии; устаревший по входу кандидат не активируется.

## Replay и живой анализ

### Replay

Seed связывает сохраненные `pack.json` v3 с точными входными снимками шести полных и трех ablation-условий. Первоначальный ответ сохраняется неизменным, а текущие проверки выполняются заново и маркируются своей версией. V04 должен демонстрировать блокировку, а не быть заранее исправленным в seed.

Replay совместим только с тем же содержанием обращения, requested_fact_keys, каталогом, порядком и составом выбранных источников и их текстами. `replay_compat_digest` вычисляется по каноническому JSON этих данных и справочного контекста: ключи объектов сортируются, порядок массивов сохраняется, UTF-8, без внутренних UUID версий БД. Он не является хешем исходного prompt; `prompt_sha` и исторический generation profile сохраняются отдельно из записанного запуска.

Измененный вход дает `REPLAY_INPUT_MISMATCH`; система не подгоняет сохраненный ответ под новые данные. Исключение заранее заданного источника позволяет выбрать соответствующий ablation replay; включение обратно возвращает совместимость с full replay. UI явно показывает выбранную запись. При произвольной новой версии текста для нее может не быть replay.

### Live

Один адаптер Responses API получает server-built snapshot и JSON Schema. API-ключ хранится только на backend в окружении; имя модели задано `OPENAI_MODEL`. Схема и параметры проверяются на выбранной модели при подключении. Refusal, incomplete output, ошибки авторизации, лимиты и таймауты нормализуются в понятные коды.

На один новый AnalysisRun — один provider request. Не использовать скрытые SDK-ретраи и автоматическую «починку» ответа повторной генерацией; явный повтор оператора создает новый run. Ошибка live не включает replay. При timeout неизвестные usage/cost сохраняются как unknown/null, а не как нулевые расходы.

Модель не получает инструменты, сеть или shell. Все исходные документы считаются данными. В приложении используются только заранее разрешенные source snapshots; текст документа не меняет инструкции и полномочия.

Сохраняются model id, provider request id если получен, prompt/schema/policy версии и хеши, входной snapshot, raw output, canonical result, timestamps, latency, usage и ошибка. Цена в деньгах выводится только при явно заданном тарифе с датой; иначе остается неизвестной.

### Выполнение и восстановление

MVP работает одним API-процессом. Сначала транзакционно создать run со снимком и `running`, затем выполнить ограниченный по времени provider call вне транзакции БД, затем сохранить результат. Начальный timeout — 90 секунд, конфигурируемый.

POST ожидает завершения. Если клиент потерял соединение, run остается доступен из списка; повтор с тем же Idempotency-Key возвращает существующий run без нового вызова. Running run возвращается с HTTP 202. Завершенный повтор — HTTP 200; первоначальное создание — HTTP 201 с итоговым состоянием.

На старте нового единственного процесса run предыдущего owner_instance_id со статусом running помечается failed/PROCESS_INTERRUPTED. Автоматического повторного вызова модели нет. Запоздалый обработчик может завершить только собственный running run через compare-and-set; он не переписывает failed или другой результат. Несколько replicas/workers и распределенная очередь не входят в MVP.

## API

Префикс `/api/v1`. Тела JSON, ошибки одной формы: `{code, message, details, request_id}`. `details` содержит безопасные field paths/версии, без секретов. Изменяющие вход/разбор/решение команды требуют `expected_case_version`; несовпадение — HTTP 409.

| Метод и путь | Назначение |
| --- | --- |
| GET `/health`, GET `/ready` | Процесс и готовность БД/миграций; отсутствие live-ключа не ломает replay readiness |
| GET `/capabilities` | replay/live availability, поддерживаемые каталоги, текущие profile versions и лимиты; без ключей |
| GET `/cases`, POST `/cases` | Список и создание учебного обращения |
| GET `/cases/{id}`, PATCH `/cases/{id}` | Карточка и изменение текста/набора проверяемых фактов/справочного контекста |
| POST `/cases/{id}/sources` | Регистрация источника, с текстом либо как ожидаемого документа |
| POST `/cases/{id}/sources/{source_id}/versions` | Новая версия текста; прежняя неизменяема |
| PATCH `/cases/{id}/sources/{source_id}` | Метаданные, включение в анализ и выбор версии; повышает content_revision |
| GET `/cases/{id}/sources/{source_id}/versions/{version_id}` | Точный текст версии и хеш для подсветки |
| GET `/cases/{id}/replay-options` | Только записи, совместимые с текущим input digest, и их происхождение |
| POST `/cases/{id}/runs` | mode, expected_case_version, replay_id для replay; обязательный Idempotency-Key |
| GET `/cases/{id}/runs`, GET `/runs/{run_id}` | История, прогресс, результат/ошибка и метаданные |
| GET `/cases/{id}/proposals` | Версии и кандидаты; происхождение и состояние актуальности |
| GET `/proposals/{revision_id}` | Body, snapshot bindings, проверки, resolved evidence и решение |
| POST `/proposals/{revision_id}/revisions` | Полный исправленный body + reason; новая операторская версия на том же актуальном входе |
| POST `/cases/{id}/active-proposal` | Явная активация актуального кандидата |
| POST `/proposals/{revision_id}/validate` | Новый ValidationCheck текущим профилем; body не изменяется |
| POST `/proposals/{revision_id}/decision` | approve/reject, reason, expected_case_version; Idempotency-Key |

Редактирование не принимает `resolved spans`, validation result, actor или approval как доверенные поля клиента. Сервер вычисляет их сам. `actor` берется из локального demo-session, а не из model output.

Ключ идемпотентности уникален в пределах операции и case_id. Сервер сохраняет хеш тела команды. Повтор ключа с другим телом возвращает `IDEMPOTENCY_CONFLICT`. Новый анализ при уже выполняющемся другом run этого обращения дает `ANALYSIS_ALREADY_RUNNING`.

Основные коды: CASE_VERSION_CONFLICT, PROPOSAL_STALE, VALIDATION_PROFILE_CHANGED, VALIDATION_BLOCKED, ALREADY_REVIEWED, REPLAY_INPUT_MISMATCH, LIVE_NOT_CONFIGURED, MODEL_REFUSAL, MODEL_OUTPUT_INCOMPLETE, INVALID_MODEL_OUTPUT, MODEL_TIMEOUT, PROVIDER_ERROR, PROCESS_INTERRUPTED. Ошибки схемы/лимитов до запуска — 422/413; ненастроенный live — 503 без provider call. Отказ при одобрении заблокированной карточки — 409.

## Лимиты и локальная среда

Начальные конфигурируемые ограничения: 8000 символов обращения; 20 источников; 20000 code points на источник; 80000 суммарно выбранных символов источников; 4096 выходных токенов модели. Превышение входа отклоняется явно; обрезки текста и незаметной потери источников нет.

Локальный demo-оператор один, actor=`demo_operator`; это не промышленная авторизация. API и UI имеют один origin, порт опубликован на 127.0.0.1, БД наружу не публикуется. Разрешенные dev-origins задаются явно; изменяющие запросы из чужого browser origin отклоняются. Перед открытием сервиса внешним пользователям потребуется отдельная задача доступа и эксплуатации.

Окружение: DATABASE_URL, APP_ORIGIN, LIVE_ENABLED=false по умолчанию, OPENAI_API_KEY, OPENAI_MODEL, MODEL_TIMEOUT_SECONDS, MODEL_MAX_OUTPUT_TOKENS и входные лимиты. `.env.example` содержит только названия и безопасные примерные значения. Секреты, локальная .env и реальные данные не попадают в Git или UI.

Один Compose-путь должен запускать replay без модели и ключей. Миграции и идемпотентный seed — явные команды. Повтор seed не перезаписывает исправленные пользователем обращения; reset demo должен быть отдельной явно названной операцией, не частью обычного запуска.

## Проверки и критерии приемки

| Группа | Обязательные сценарии |
| --- | --- |
| Доказательства | Несмежные фрагменты по отдельности; запрет склейки; отрицание в промежутке; чужой source_id; неоднозначная цитата; устаревший хеш/версия |
| Время | sent/received/occurred; часовые зоны; неверное время без буквальной опоры; обязательные события и допустимые дополнительные |
| Согласованность | alternative_accepted без confirmed, в том числе при отсутствии факта; повторный lookup снимка; требование тихого номера и окон во двор вместе |
| Представление | 12000 minor → 120.00 USD; emoji перед фрагментом; несколько выделений в одном документе; безопасный показ HTML-подобного текста |
| Версии/БД | Две вкладки редактируют одну версию; source update делает решение историческим; approve одновременно с правкой; запоздалый model run не затирает решение оператора |
| Режимы | Replay не вызывает провайдера; измененный input не воспроизводит чужой ответ; отказ live не включает replay; повтор ключа не вызывает модель снова |
| Ошибки | Refusal, incomplete/invalid JSON, timeout, неизвестный usage, перезапуск во время run; видимый результат без тихого ретрая |
| UI end-to-end | Просмотр доказательств, исправление блокирующей ошибки, подтверждение новой версии, отклонение с причиной, возврат к историческому snapshot |

Runtime-тесты независимы от сети. Unit/integration/e2e CI выполняются на каждом изменении. LLM eval — отдельная явная команда с лимитом вызовов и версиями, не часть обычного smoke CI. Для live-профиля сначала проверить совместимость схемы и известные проблемные кейсы; будущие данные для проверки обобщения хранить отдельно от набора разработки.

Исходные 19 тестов и девять записанных условий — материал для переноса, а не весь набор тестов приложения. Добавить проверки границ HTTP, транзакций и UI. В eval отдельно показывать значения фактов, достаточность доказательств, полноту хронологии, следующий шаг и общий результат; высокий один показатель не заменяет остальные.

Готовое демо показывает минимум три истории: корректный разбор с источником; отсутствие подтверждения и полный запрос; противоречие модели, блокировка, исправление оператором и подтверждение новой версии. Ошибочный V04 из записи сохраняется и остается наглядным примером работы guard.

## Порядок реализации

1. **Bootstrap и контракт.** Создать самостоятельный проект, перенести Pydantic-контракт, validators и положительные/отрицательные тесты. Сохранить измеренную базу v3, записи и их manifest неизменными.
2. **Версии и replay API.** Миграции, seed, source snapshots, run/proposal/decision, идемпотентность и optimistic concurrency. Получить полный путь через HTTP без live-ключей.
3. **Операторский интерфейс.** Список, карточка, подсветка, редактор доказательств, требования, история, блокировки и решения. Проверить три демонстрационные истории end-to-end.
4. **Живой адаптер.** Настроить API-доступ и модель, зафиксировать профиль, обработать ошибки, провести ограниченные evals актуальной инструкции. Replay остается отдельным режимом.
5. **Упаковка портфолио.** Чистый запуск, README, короткое видео, архитектурные решения, измерения с ограничениями и воспроизводимые проверки.

Этапы заканчиваются работающим результатом, а не списком поднятых сервисов. Для публичного релиза нужны работоспособный replay и проверенный на выбранном доступе live-путь; пока доступа нет, честно маркируется replay milestone, а не готовность live. Лицензия, публикация GitHub и развертывание определяются автором отдельно от начала локальной разработки.

# Офлайн-прототип допустимых ответов модели

У каждого обращения свой список фактов и источников, которые можно запросить.
Прототип превращает эти списки в ограничения ответа. Скрипт проверяет их через
отдельный профиль. Демо продолжает работать на v3.2.
[Настройка профиля](../live-provider.md#отдельная-проверка-ограничений-v33).

## Как устроен прототип

- Уже включённые источники остаются во входе для цитирования. Из прочих источников
  во вход попадают только подходящие, которые заранее указаны в доверенном
  списке. Модель видит их карточки без текста. Прототип проверяет, что источник
  относится к этому обращению и ещё не включён. Доверенный список для V01
  задан вручную по проверочному кейсу в настройках backend.
- В схеме запроса действие и адрес источника идут парой. Например, подходящее
  письмо можно запросить действием `read_source`. Для журнала и платёжного
  реестра действия определяются их типом. При пустом списке доступны
  `ask_user` и `none`, оба без адреса источника.
- Модель заполняет в объекте `facts` ровно поля из `requested_fact_keys`.
  Прототип проверяет список ключей и переводит этот объект в обычную карту
  Proofline со списком фактов. Для проверки этой карты используется действующий
  валидатор. Общая схема приложения сохранена.

## Проверка на трёх кейсах

| Кейс | Что отклонили | Что приняли |
| --- | --- | --- |
| V02 | Повторный запрос уже включённого журнала, даже если он ошибочно попал в доверенный список. Пропуск запрошенного факта. | Оба запрошенных факта и просьбу прислать письмо с подтверждением доставки. |
| V04 | Ответ с тремя лишними фактами. | Один запрошенный факт об условном согласии и просьбу подтвердить тихий номер с окнами во двор. |
| V01, ответ клиента ещё не включён | Неверное действие для нужного письма. Запрос нерелевантного платёжного документа того же типа, который тоже ещё не включён. | Запрос оригинала ответа клиента по известному адресу. |

Для V02 и V04 взяты снимки прогона v3.3. Принятые варианты составлены вручную
на копиях для проверки ограничений. V01 использует замороженный вариант
с исключённым оригиналом письма и специально добавленный в памяти лишний документ.
Исходные записи каждого прогона сохранены.

SDK собрал три запроса на подставном HTTP. Локальная проверка Ajv применила
фактическую JSON Schema из каждого запроса к подходящим и неподходящим ответам.
Три подходящих примера также прошли преобразование в обычную карту и её
валидацию. Модельных вызовов — **0**.

Проверка показала и границы. Пустая хронология в V02 по-прежнему допустима.
В V04 один запрошенный факт вместе с лишними вопросами тоже проходит эту схему.
Полнота хронологии, достаточность цитат и уместность вопросов остаются задачами
смысловой проверки. Совместимость временной схемы с Groq ещё предстоит проверить.

Запуск из корня проекта с установленными локальными зависимостями Python и
frontend. Ajv берётся из уже установленного набора frontend.

```sh
uv run --locked --offline python scripts/prototype_model_choices.py
```

## Следующее действие

Профиль подключён отдельно. Офлайн-тест на PostgreSQL подтвердил раздельное
хранение исходного ответа и карты, включая ошибочные ответы без карточки.
Следующий шаг — отдельно согласовать один запрос V01 на Groq Free. Он проверит,
принимает ли API временную схему и может ли модель выбрать доступное нужное
письмо. После этого есть смысл проверить V02 и V04 на тех же ограничениях.

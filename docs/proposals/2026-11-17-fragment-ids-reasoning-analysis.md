# ID фрагментов или reasoning: минимальный следующий шаг

17 ноября 2026 года. Offline-разбор по запросу автора. **Новых модельных вызовов —
0.** Продуктовый код, настройки, схема, существующие документы и результаты не
менялись. Docker/SQL-команд и чтения ключей не было. Читались публичная документация
и сохранённые ответы; два SDK-запроса направлены только в HTTP transport в памяти.
Этот документ — предложение следующего изменения, не его реализация.

## Выбор

**Первым добавить опциональный `GROQ_REASONING_EFFORT`, сохранив default unset.**
Первый кандидат для последующей проверки — `qwen/qwen3.8-27b` с явным `medium`,
тем же v3.2, полной схемой, лимитом 4096 и прежними критериями V02/V04.
Настройка делает effort контролируемым параметром; улучшение качества остаётся
проверяемой гипотезой. Запуск сейчас не разрешён и не выполнялся.

ID фрагментов оставить следующим отдельным вариантом. Они могут гарантировать
дословность выбранного спана, но основной непройденный критерий — смысл и полнота
разбора — такой гарантии не получает. Переход затрагивает больше контрактов и
сохранение raw/canonical, чем один необязательный параметр запроса.

## Основания в текущем коде и ответах

В [Groq adapter](../../src/proofline/providers/groq_chat.py) поле
`reasoning_effort=provider-default` записывается только в generation profile.
В HTTP request его нет. Это метка приложения, а не запрошенный effort или
подтверждение фактического режима сервера. В [Settings](../../src/proofline/config.py)
reasoning-настройки сейчас нет.

| Сохранённая попытка | Reasoning tokens из API | Completion tokens | Завершение |
| --- | --- | --- | --- |
| GPT-OSS V02 | 2426 | 2927 | stop |
| GPT-OSS V04 | 1224 | 1587 | stop |
| Qwen V02 | не сообщены | 616 | stop |
| Qwen V04 | не сообщены | 261 | stop |

GPT-OSS уже использовал reasoning. У Qwen отсутствие breakdown не равно нулю.
Все четыре ответа завершены нормально ниже лимита 4096: наблюдений обрезания
этих ответов нет. Увеличение output limit не является обоснованным исправлением
уже найденных ошибок.

В [Groq API Reference](https://console.groq.com/docs/api-reference#chat-create-request-body)
у GPT-OSS default указан как medium, у Qwen 3.8 — none; обе модели поддерживают
low/medium/high. Для Qwen high отображается в native xhigh. Неподдерживаемое
значение вызывает 400. При этом [карточка Qwen](https://console.groq.com/docs/model/qwen/qwen3.8-27b)
описывает default как thinking mode, а [reasoning guide](https://console.groq.com/docs/reasoning)
пишет, что при default Qwen не возвращает reasoning tokens. Публичные описания
неоднозначны; прежнему run нельзя задним числом присвоить none или medium.
Явный medium устраняет неопределённость **запрошенного** режима следующей проверки.

В том же guide формат показа reasoning отделён от effort. `include_reasoning`
управляет включением reasoning в ответ, не является переключателем его глубины;
его нельзя совмещать с `reasoning_format`. GPT-OSS не поддерживает reasoning_format.
Отдельные reasoning-поля уже исключаются adapter из JSON карточки.
Перенос инструкции из system message, изменение sampling и запрос текста
рассуждений в этот минимальный scope не входят.

## Какие ошибки затронет каждый вариант

| Наблюдение | ID фрагментов | Явный reasoning |
| --- | --- | --- |
| GPT-OSS V02: форма ошибочно признана отказом, неверный ready_for_rules | Точный ID может указывать на тот же недостаточный текст | Может помочь оценить смысл; гарантии нет |
| GPT-OSS V04: предложение подтверждено только временем | ID строки времени тоже дословен, но не доказывает предложение | Может улучшить выбор доказательств; нужна генерация |
| Qwen V02: отправка процитирована, отдельного события нет | Восстановление цитаты не добавляет событие | Может улучшить полноту; нужна генерация |
| Qwen V04: перенос строки заменён пробелом | Выбранный допустимый ID восстанавливает точный исходный текст | Дословность не гарантирует |
| Qwen V04: дубликат неверного факта, пустая хронология, повторное чтение | При замене только evidence-формата эти ошибки сохраняются | Потенциальное влияние на следование правилам, без гарантии |

Отзывы [GPT-OSS](../live-acceptance-groq-chat-2026-11-17.md) и
[Qwen](../live-acceptance-qwen-2026-11-17.md) не переоцениваются: 0/2 полных passes
у каждого по прежним критериям. Это по одной попытке на кейс, не оценка общей
способности модели. Снижение строгости критериев или добавление веток по V02/V04
не предлагается.

## Что потребуют ID фрагментов

Рабочая идея: сервер создаёт каталог точных спанов выбранных immutable SourceVersion.
Модель возвращает ссылки на спаны; сервер копирует исходные символы по этим ссылкам.
Ссылка должна быть связана с input/case, source/version, SHA256 и границами Unicode
code points. Неизвестные, исключённые, чужие или устаревшие ссылки отклоняются.
Повторения и неоднозначность остаются предметом явной проверки.

В in-memory иллюстрации выбран спан исходного сообщения V04 с сохранённым `\n`.
При разрешении ссылки получена точная уникальная подстрока. Unknown ID, чужой case,
stale version и неправильный hash отклонены. **Модель эту ссылку не выбирала**;
это демонстрация механизма, не исправленный результат Qwen. Исходная карточка
повторно проверена без изменений и сохраняет все три blocking codes.

Полноценный вариант должен отдельно решить:

- Детерминированную сегментацию и её версию. Строка с одним временем может быть
  слишком узкой, целый документ — слишком широким. Произвольный выбор «удачных»
  фрагментов только для известных кейсов недопустим.
- Границы каталога и размер входа. ID/enum увеличивают input, а выбранные спаны
  должны содержать каждый нужный смысл и время. Не каждый существующий fragment
  обязан совпасть с одной строкой или параграфом.
- Отдельный внутренний model wire contract с refs и новую инструкцию для него.
  Публичный AssemblyOutput с текстовыми fragments можно сохранить, но текущая
  схема **модельного** ответа уже будет другой. Подмена строк fragments на ID
  под прежним schema/profile вводила бы в заблуждение.
- Raw и canonical: сохранить настоящий ответ с ID, отдельно — результат
  детерминированного разрешения, версию resolver и hashes. Сейчас
  [RunService](../../src/proofline/application/runs.py) разбирает raw как AssemblyOutput,
  а [archive verifier](../../scripts/verify_live_archive.py) сверяет raw JSON с body.
  Нельзя представить расширенный текст как исходный ответ модели.
- Не дополнять автоматически факты или пропущенные события. Разрешение ID —
  отображение выбранной ссылки в текст, не семантическая починка ответа.

Такой вариант потребует внутренних DTO, преобразования, изменений обработки run
и проверки новых архивов, плюс unit/PostgreSQL tests. Миграция исторических
ответов не нужна и не допускается. Уже имеющиеся exact-fragment validators
поймали ошибку Qwen; ID улучшают удобство получения корректной цитаты, но не
заменяют проверки достаточности и решение оператора.

## Минимальный будущий patch для reasoning

Предлагаемый scope после отдельного разрешения на реализацию:

1. `Settings`: `GROQ_REASONING_EFFORT` необязателен; unset/пустая строка означает
   отсутствие поля в request. Допустимы low/medium/high — общий документированный
   набор для двух проверяемых Groq-моделей. Остальные значения отклоняются при
   конфигурации. Отдельный реестр моделей или универсальная система reasoning
   для всех провайдеров не нужны.
2. Только Groq передаёт настроенный effort. OpenAI/DeepSeek/Anthropic request bodies
   сохраняются. При unset прежний Groq wire body и default-профиль также сохраняются.
3. Для явно заданного effort — отдельный request profile, запрошенное значение
   с понятным происхождением и request hash, включающий параметр. Серверный
   эффективный effort не объявляется измеренным. Policy/prompt/schema hashes прежние.
4. Compose передаёт необязательную переменную, `.env.example` и provider docs
   объясняют её. `reasoning_effort` добавляется как известный param в закрытый
   allowlist диагностики; error body, message и произвольные значения не сохраняются.
5. Parser и validators, один запрос, deadline, max_retries=0, отсутствие fallback,
   человеческое решение и формат сохранённых предложений остаются прежними.

Это несколько правок существующих модулей конфигурации/adapter/diagnostics,
Compose и тестов. Новые продуктовые DTO, публичная схема, БД и UI не требуются.
Короткий отдельный SDK runner мог бы проверить параметр, но не продемонстрировал
бы штатный AnalysisRun и операторский workflow; для app-приёмки выбран обычный путь.

Проверки будущего patch до сети: unset/blank/invalid config; Groq-only wire diff;
строгая схема и неизменные текстовые hashes; достоверный profile/request hash;
безопасный 400; length/refusal/timeout без повторов; failed/succeeded run и
идемпотентность на PostgreSQL; старые archives. Затем обязательные проверки
репозитория. Сейчас эти изменения не внесены.

## Offline-проверка осуществимости и пределы

OpenAI SDK 2.54.0 сериализовал Qwen medium и GPT-OSS high в два **in-memory HTTP**
запроса. Реальный HTTP был программно запрещён, ключ — фиктивный, generate
приложения не вызывался. В каждом теле добавлено только reasoning_effort;
strict, лимит 4096, prompt и schema hashes остались прежними. Фиктивный ответ
не оценивался как карточка и не является новым результатом модели.

Проверка подтверждает возможности клиента. Она не доказывает принятие сочетания
effort+полной схемы сервером, фактическую глубину reasoning или улучшение качества.
Эффект нельзя получить повторной оценкой старых ответов: нужна новая генерация.

## Следующий шаг

**Реализовать только опциональный Groq effort и проверить patch без модельных
вызовов.** ID-контракт, policy v3.2, схема, sampling и лимит 4096 остаются вне patch.
Это следующий предлагаемый scope, сейчас выполнен только разбор.

После успешных offline checks — отдельно согласовать Qwen medium, V02/V04,
максимум два запроса, $0, новый экземпляр и архив, остановку на технической ошибке.
Сохраняются исходные критерии. Начать с medium: Qwen high соответствует native
xhigh и может сильнее давить на ограниченный completion budget.

По наблюдавшимся input tokens Qwen (2109/2081), input + cap 4096 составляет
6205/6177. Это ниже опубликованного Free TPM 8000, но является расчётом планирования,
не гарантией server admission: точные account limits могут отличаться.
[Квоты Groq](https://console.groq.com/docs/rate-limits). Между началами оставить
не менее 65 секунд. Reasoning расходует completion budget; при length/таймауте
остановиться, без автоматического повышения лимита или повторной генерации.

Новый medium-прогон не станет принятием этапа 4 по одному удачному кейсу. Если
полный бар не пройден, сохраняем результаты и выбираем дальнейшую работу по
наблюдаемому классу ошибки, без автоматического расширения числа вызовов.

локальные receipts с аудитом и иллюстрациями находятся в игнорируемом notes и
не нужны для использования или понимания приложения. Контейнеры и БД не открывались,
исторические файлы только читались, credentials не читались. Полная проверка
приложения заново не заявляется: продуктовый код не менялся.

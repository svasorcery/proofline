# Кандидат v3.3 для следующей проверки Proofline

17 ноября 2026 года подготовлен полный текст инструкции для отдельного прогона.
Изменены два раздела кандидата. Действующая инструкция и формат запроса
сохраняются до отдельного подключения кандидата.
[Кандидат v3.3](2026-11-17-live-policy-v3.3-candidate.txt).

## Что изменилось

| Наблюдение | Правка в кандидате |
| --- | --- |
| В V02 модель предложила перечитать включённый журнал поставщика как документ | Источник нового подтверждения выбирается из записей `catalog` с `included=false`. Действие определяется полем `kind`. Связь с недостающим подтверждением оценивается по метаданным каталога. |
| В V02 отдельно не показана отправка формы, в V04 отправка опиралась только на заголовок `Date` | Короткий пример показывает два события с собственными доказательствами. У каждого свои время, роль и фрагменты, связывающие событие с тем же ответом клиента. |

Для `document` выбирается `read_source`, для `provider_log` — `query_provider`,
для `payment_ledger` — `query_payment`. Модель копирует `locator` из подходящей
записи. Если среди записей нет источника для недостающих подтверждений, она
выбирает `ask_user`, передаёт `locator=null` и перечисляет все подтверждения.
В полном снимке V02 и V04 все записи уже включены. Для этих кейсов выбор —
`ask_user` с прежними наборами требований.

Пример использует отдельное вымышленное сообщение о месте встречи. Строка
отправки и текст ответа связывают событие с сообщением. Квитанция получения
с тем же ID и фрагмент текста подтверждают второе событие. Когда известен только
один момент, инструкция требует показать только подтверждённое событие.

## Что проверено offline

- Дословные фрагменты из примера и оба события принял текущий валидатор.
  Подстановка доказательства получения в событие отправки дала
  `time_not_in_fragments`. Варианты с одним известным временем тоже допустимы.
- Для каждого из трёх типов проверены подходящий источник вне снимка,
  включённый источник, несовпадающий тип действия и неизвестный locator.
  Проверен `ask_user` без locator. На копиях ответов V02 и V04 подставлены
  ожидаемые действия и наборы требований. Прежние ответы сохранены побайтно.
- Проверены контрольные суммы 266 существующих файлов, включая действующую
  v3.2 и все пять live-архивов. Схема совпала с замороженным контрактом.
  Контейнеры и БД в этом разборе не использовались. Модельных вызовов — **0**.

Локальный валидатор проверяет форму, принадлежность источника, тип lookup,
дословность и наличие нужного времени. Полнота хронологии и достаточность
цитаты по смыслу остаются отдельными критериями приёмки.

В модель передаётся только текст между маркерами BEGIN и END. При извлечении
по правилам действующего профиля тело кандидата занимает 7576 байт UTF-8
против 5989 у v3.2. SHA256 тела кандидата
`2d9b47d44aa0172a8c75ef6a5283009045695c088a174256ae9f4408abb691d3`.
SHA256 инструкции с нынешним префиксом
`4f1849841208622264bdc0d4c963626403bfc1f6da30343d459235fd23530269`.
Это идентификаторы кандидата для будущего прогона.

## Следующий шаг

Подготовить отдельный тестовый профиль v3.3, сверить его запрос offline с архивом
Qwen `medium` и убедиться, что среди параметров генерации меняется только текст
инструкции. После отдельного согласования выполнить V02, затем V04 на тех же
настройках Groq Free, максимум два запроса и $0. При первой технической ошибке
остановиться. Для V02 проверить отдельную отправку формы и `ask_user`, для V04 —
все три события и доказательство отправки, которое связывает время с ответом
клиента. Оценка остальных критериев остаётся прежней.
